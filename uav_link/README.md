# uav_link — бортовий маршрутизатор каналів керування БПЛА

Один процес володіє UART польотного контролера й обслуговує **обидва** канали
керування одночасно:

| канал | середовище | роль |
|---|---|---|
| **A** | радіо 433 МГц, SiK на `/dev/uav_radio` | резерв, не залежить від жодної інфраструктури |
| **B** | LTE + тунель WireGuard → концентратор `10.8.0.1` | основний, обслуговує кілька наземних станцій |

Перемикання автоматичне (за втратою і за деградацією затримки) або за командою
оператора, з гістерезисом і трирівневим захистом від втрати зв'язку.

## Збирання

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Під ARM64 з ноутбука — `-DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-linux-gnu.toolchain.cmake`.
Залежностей немає: тільки стандартна бібліотека C++17 і POSIX.

## Встановлення на Raspberry Pi

```bash
sudo cmake --install build
sudo systemctl daemon-reload
sudo systemctl enable --now uav-link
journalctl -u uav-link -f
```

## Керування під час роботи

```bash
printf 'STATUS' | nc -u -w1 10.8.0.2 14552   # режим, активний канал, затримки
printf 'A'      | nc -u -w1 10.8.0.2 14552   # ручний перехід на радіо
printf 'AUTO'   | nc -u -w1 10.8.0.2 14552   # повернути автоматику
```

Команди приймаються лише з адрес у `control_allow`. Станція-спостерігач
каналами не керує — те саме розмежування прав, що й у концентраторі.

## Будова

```
main.cpp        точка входу, сигнали, конфігурація
Router          подієва петля epoll: єдиний власник усіх дескрипторів
  ITransport      спільний інтерфейс каналу
    SerialTransport   послідовний порт (контролер, радіомодем)
    UdpTransport      сокет у тунелі з фільтром джерела
  IcmpProbe       вимір повного шляху борт <-> оператор
  MavlinkFramer   потік байтів -> цілі кадри v1/v2
  LinkMonitor     живість, затримка, якість ефіру - окремо на кожен канал
  Arbiter         правило вибору каналу з гістерезисом
  Failsafe        рівні 2 і 3 захисту
```

**Однопотокова подієва петля.** У програмі немає жодного м'ютекса, бо немає
спільних даних між потоками: усі дескриптори — послідовні порти, сокети,
таймери — обслуговує один `epoll_wait`. Немає ні перегонів, ні пріоритетної
інверсії, ні розкиду затримки від блокувань. Прототип на Python тримав вісім
потоків і мусив серіалізувати запис в UART замком.

**Немає виділення пам'яті в гарячому шляху.** Буфери розбирача — `std::array`
фіксованого розміру, тексти рішень арбітра — фіксовані масиви символів.
Єдиний `std::vector` — черга телеметрії, і йому ємність резервується на старті.

## Виміряні константи

Усе, що стоїть у `config/uav_link.conf`, здобуто на стенді, а не вибрано з
міркувань зручності:

| величина | значення | звідки |
|---|---|---|
| потік телеметрії | 2 070 Б/с | `MAV_1_MODE = Normal`, `MAV_1_RATE = 2500` |
| канал A під навантаженням | 2 056 Б/с, txbuf 91–100 %, помилок 0 | 8 вікон по 30 с |
| запас за сигналом каналу A | 88 дБ | стенд, антени за метр |
| повний обіг каналу A | 160,9 мс | віддалена команда AT через ефір |
| повний шлях каналу B | 126,8…197,8 мс | 14 вимірів за ніч |
| наземна ділянка | 63,8…73,0 мс | різниця `ping 10.8.0.3` і `ping 10.8.0.1` |
| час виявлення втрати | **2,85 ± 0,14 с** | 4 повтори |
| час повернення | **10,75 ± 0,06 с** | 4 повтори |
| втрати при перемиканні | **0 байтів** | сума потоків обох каналів у вікні переходу |

Розкид часу виявлення — це фаза передавання наземної станції, а не дрижання
алгоритму: три з чотирьох вимірів лягли в 6 мс один від одного.

## Багаторівневий захист

1. **Рівень 1** — перемикання на резервний канал.
2. **Рівень 2** — обидва канали мовчать: маршрутизатор перестає приховувати
   втрату, PX4 бачить зникнення HEARTBEAT наземної станції і відпрацьовує
   власний `NAV_DLL_ACT`.
3. **Рівень 3** — PX4 не відреагував за `failsafe_sec`: маршрутизатор сам
   надсилає `MAV_CMD_NAV_RETURN_TO_LAUNCH`. За умовчанням лише пишеться в
   журнал (`failsafe_action = log`).

## Чому живість визначається лише прийманням

Під час досліду 18.09 канал B блокувався правилами фаєрвола. За чотири секунди
до перемикання близько 8,5 КБ телеметрії пішли в нікуди, і `sendto` **щоразу
повернув успіх**: пакет відкидається вже після того, як сокет його прийняв.
Так само поводиться реальна втрата покриття. Отже система не може дізнатися
про обрив із власних викликів передавання — єдиний доказ того, що канал живий,
це трафік, який приходить назад.
