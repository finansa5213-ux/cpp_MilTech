# ДЗ16 (Заняття 32) — робота з I²C-пристроєм MPU-6050

Повний ланцюжок від пошуку пристрою на шині до фізичних величин, написаний
власним кодом поверх `i2c-dev`. Готових бібліотек датчика (`Adafruit_MPU6050`
тощо) не використано — кожна транзакція на шині видима в коді.

## Що зроблено

| Вимога ТЗ | Де реалізовано |
|---|---|
| Відкрити шину й обрати адресу | `LinuxBus::open()`, `LinuxBus::selectDevice()` — `open()` + `ioctl(I2C_SLAVE)` |
| Двофазне читання регістра | `LinuxBus::readBlock()` — `write(reg)` → `read(data)` |
| Звірка ID | `Mpu6050::checkId()` — WHO_AM_I (0x75) має віддати 0x68 |
| Блок вимірів і збирання 16-бітних значень | `Mpu6050::read()` + `be16()` — 14 байтів з 0x3B, старший байт першим |
| Перерахунок у фізичні величини | `Mpu6050Convert.hpp` — g, °/с, °C за чутливістю з даташита |
| Обробка помилок | `i2c::Error` + `describe()` — немає ACK, обрив читання, невірний ID, непідтверджений запис |
| Людиночитний вивід кілька разів на секунду | `main.cpp`, типово 5 Гц, `--hz` змінює |

Чому шина за інтерфейсом, а не напряму: три сценарії відмови з ТЗ (немає ACK,
обрив читання, невірний ID) на живій шині відтворити важко, а на симуляторі —
неможливо. `FakeBus` у тестах відтворює їх усі за пів секунди.

## Збірка

У кореневий `CMakeLists.txt` репозиторію додати рядок:

```cmake
add_subdirectory(homework_16)
```

Далі як завжди:

```bash
cmake --preset debug
cmake --build --preset debug --target homework_16 mpu6050_tests
```

Тести:

```bash
ctest --test-dir build/debug --output-on-failure -R "Be16|Convert|Driver"
```

## Запуск

Спершу переконатися, що пристрій узагалі видно на шині:

```bash
i2cdetect -y 1
```

Під симулятором (Windows — усе всередині WSL):

```bash
LD_PRELOAD=./libi2csim.so ./homework_16 /dev/i2c-1 0x68
```

На реальній платі — той самий бінарник без `LD_PRELOAD`:

```bash
./homework_16 /dev/i2c-1 0x68
```

### Опції

| Опція | Призначення |
|---|---|
| `--hz N` | частота опитування, типово 5 |
| `--samples N` | зупинитися після N кадрів (для CI та логів) |
| `--accel-range N` | 2 / 4 / 8 / 16 g |
| `--gyro-range N` | 250 / 500 / 1000 / 2000 °/с |
| `--ignore-id` | продовжити, навіть якщо WHO_AM_I не 0x68 |
| `--no-init` | не писати в регістри (якщо шина лише для читання) |
| `--scan` | пройти адреси 0x03..0x77, спрощений аналог `i2cdetect` |
| `--raw` | додатково показувати сирі байти блоку |

## Коди повернення

| Код | Значення |
|---|---|
| 0 | успішно |
| 1 | помилка в аргументах |
| 2 | помилка шини або пристрою |
| 3 | WHO_AM_I не збігся (і не задано `--ignore-id`) |

## Обробка помилок

- **Немає ACK.** Ядро віддає `ENXIO`/`EREMOTEIO`/`ENODEV` — програма розрізняє
  це від інших відмов і друкує «пристрій не відповідає на шині (немає ACK)»
  разом з `errno` і поясненням.
- **Обрив читання.** Якщо `read()` повернув менше байтів, ніж запитано, це
  `ShortRead` — кадр не декодується, бо піврозібраний блок гірший за відсутній.
- **Невірний ID.** Обмін пройшов, але значення не те: окремий код `BadId`,
  щоб не плутати «пристрою немає» з «пристрій не той».
- **Запис не подіяв.** Окремий код `NotApplied`: запис пройшов з ACK, але
  перечитування дало інше значення. Саме так поводиться курсовий симулятор із
  регістрами діапазонів.
- **Серія збоїв.** П'ять невдалих читань поспіль зупиняють програму, щоб вона
  не крутила нескінченний цикл помилок.

## Ключове рішення: довіряй перечитаному, а не записаному

Після запису в `GYRO_CONFIG` (0x1B) і `ACCEL_CONFIG` (0x1C) програма
**перечитує ці регістри** і бере за основу перерахунку той діапазон, який
пристрій підтвердив, а не той, який ми просили.

Це не перестраховка. Курсовий `libi2csim.so` приймає запис у ці регістри з ACK,
але не зберігає його — відліки й далі приходять у шкалі ±2 g. Наївна реалізація
поділила б їх на чутливість «замовленого» ±8 g і показала б 3.98 g замість
1.00 g при нерухомому датчику на столі. Помилка в чотири рази, і жодного
повідомлення про збій.

Те саме зроблено з пробудженням: після запису 0x00 у `PWR_MGMT_1` регістр
перечитується, і якщо біт SLEEP лишився піднятим — це помилка, а не тиша.

## Спостереження за курсовим симулятором (libi2csim.so, x86-64)

Перевірено на бібліотеці з комплекту заняття. Корисно знати заздалегідь:

| Що | Поведінка симулятора | Наслідок |
|---|---|---|
| Адресація | На **будь-яку** адресу, крім 0x48, відповідає як MPU-6050 | Сценарій «немає ACK» на симуляторі не відтворюється — перевіряється лише юніт-тестами через `FakeBus` |
| `--scan` | Відповідають усі 117 адрес | Програма це помічає й прямо каже, що ви під симулятором |
| 0x48 | ADS1115: читання регістра 0x75 дає **0x85** | Верхній байт config-регістра 0x8583 — вказівний регістр ADS1115 має лише 2 біти, тож 0x75 маскується в 0x01. Програма коректно рапортує невірний ID і виходить з кодом 3 |
| `PWR_MGMT_1` (0x6B) | Зберігається: до пробудження читається 0x40 (SLEEP), після — 0x00 | Крок пробудження змодельовано чесно |
| `GYRO_CONFIG` / `ACCEL_CONFIG` | Запис приймається, але **не зберігається** — завжди 0x00 | Саме тому перерахунок ведеться за перечитаним значенням |
| Температура | Стала: сирі байти `F0 B0` = −3920 → рівно 25.00 °C | Підтверджує формулу `raw/340 + 36.53` |
| Виміри | Живі, повільно змінюються; az ≈ 0.99 g | Датчик «лежить горизонтально» |

## Примітки щодо заліза

- Після подачі живлення MPU-6050 **спить**, і всі виміри — нулі. Тому перед
  читанням програма пише 0x00 у `PWR_MGMT_1` (0x6B). Якщо запустити з
  `--no-init`, у виводі будуть саме нулі — це нормальна перевірка гіпотези.
- `--scan` пробує читати регістр 0x00 з кожної адреси. На реальній шині це
  діагностика «на швидку руку»: еталонний інструмент — `i2cdetect -y N`.
  Деякі мікросхеми на читання з 0x00 реагують побічним ефектом, тож на
  незнайомій шині краще користуватися `i2cdetect`.
- Адреса 0x69 замість 0x68 — це MPU-6050 з підтягнутим виводом AD0.
